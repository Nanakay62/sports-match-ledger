# ADR-0019: Real-Time vs. Digest Alert Delivery

## Status
Accepted

## Context
ADR-0018 built four of the handbook's five named paywall walls (§18.3) but deliberately left "real-time alerts" ungated, because no alert feature — digest or real-time — existed anywhere in the codebase to gate: no SMTP integration, no third-party email provider, no per-user notification model. Building a toggle that unlocked nothing would have been worse than leaving it as pricing-page copy. This ADR closes that gap for real.

The obvious risk in building this now is inventing a fake integration — claiming "real-time alerts" work when there's no actual credential to send anything anywhere. No email provider account or SMTP credential was available. The design below resolves that the same way ADR-0017 resolved the equivalent problem for billing: build the real mechanism, make it safe and fully functional with zero external credentials, and make the real delivery path a matter of configuration rather than new code once a credential exists.

## Decision
1. **A pluggable email backend** (`packages/notifications/email_backend.py`): `ConsoleEmailBackend` is the default — it never fails, needs no credentials, and writes every message to `data/emails/` as a real file plus an in-memory record, so the full pipeline is genuinely testable end to end. `SMTPEmailBackend` is a complete, real `smtplib` implementation that activates automatically the moment `SMTP_HOST` is set in the environment — no code change required to go live, matching the Stripe pattern.
2. **Server-side subscriptions, separate from the client-only watchlist**: `AlertSubscriptionModel` (`packages/database/models.py`) records an email against an event the moment that email is known and the visitor adds it to their watchlist (`apps/web/lib/alerts.ts`, wired into `watch-button.tsx`). This has to be server-side — an email cannot be delivered to a browser's `localStorage` — while the UI watchlist itself correctly stays client-only per ADR-0018's own reasoning.
3. **`NotificationDispatcher`** (`packages/notifications/dispatcher.py`) is the single decision point: on a status change, every subscriber's *persisted* entitlement (never a client-supplied flag) decides delivery — `is_pro and status == "active"` sends immediately; everything else, including no entitlement record at all, queues into `DigestQueueItemModel` for the next daily batch. A lapsed Pro subscription (`past_due`) is explicitly tested to fall back to digest, not to keep real-time delivery on a technicality.
4. **Wired into the actual status-change point**, not a synthetic trigger: `workers/pipeline/evidence_lane.py` calls the dispatcher immediately after `event.status` changes and commits, wrapped in a try/except that logs and never blocks publication — a notification failure must never prevent an event from publishing.
5. **`scripts/send_daily_digests.py`** batches every free subscriber's pending items into one email (not one per update) and marks them sent, mirroring the existing `scripts/generate_newsletter.py` pattern. It is not self-scheduling — a cron/scheduled task must run it daily, same as the newsletter script.

## Consequences
- **Positive**: "Free: daily digest / Pro: real-time" (Handbook §18.1) is now a real behavioural difference, not marketing copy, verified live: subscribing via the running API, triggering a real status change through `EvidenceLaneWorker`, and confirming a real file appeared in `data/emails/` with the correct recipient and content — not just a unit test in isolation. 11 new tests, including one that exercises the actual `evidence_lane.py` wiring end to end and one that runs the real digest script against seeded data.
- **Negative / follow-ups, stated explicitly**: no email has ever been sent through a real SMTP provider — `SMTPEmailBackend` is implemented and unit-testable but has not been exercised against a live mail server, since no credential exists to test it with. The daily digest script has no scheduler wired to it (needs a cron entry or equivalent once deployed). There is no unsubscribe link inside the emails themselves — unsubscribing today only happens by removing the item from the watchlist UI, which is a real gap for anyone who receives a digest without the app open in another tab.
