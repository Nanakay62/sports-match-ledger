# ADR-0017: Stripe Billing Integration and Persisted Entitlements

## Status
Accepted

## Context
Handbook Phase 10 (§18) requires the paid tier to actually work: real checkout, real webhook-driven entitlements, and self-service cancellation ("never dark-pattern the cancellation" — §2.4). Prior to this ADR, `apps/api/app/routers/billing.py` was a complete mock: entitlements lived in an in-memory `dict` that reset on every server restart or redeploy, the webhook handler validated a generic HMAC signature against a fake `Paddle-Signature` header that no real payment processor sends in that form, and the frontend's "Subscribe" button (`apps/web/components/pro-cta.tsx`) explicitly said "Demo build: no billing is wired up" and did nothing.

The handbook recommends Paddle as a merchant of record specifically because it absorbs EU VAT handling. This build uses **Stripe** instead, per the account actually available to run and test this integration against. This is a conscious deviation from the handbook's recommendation, not an oversight: Stripe does not handle EU VAT automatically (that requires Stripe Tax, a separate paid add-on not configured here), so VAT compliance for EU consumer sales remains an open item before real revenue should flow through this integration — tracked as a follow-up below, not solved by this ADR.

There is also no accounts/sign-in system in this codebase. Building full passwordless email authentication (magic links, session cookies) was assessed as materially larger scope than "billing" and deferred; this phase identifies a paying customer by email only, matching the handbook's own minimum bar ("Passwordless email sign-in is sufficient" — §18.1) while keeping the identity model as simple as it can be and still be real.

## Decision
1. **Stripe over the `stripe` SDK, via raw REST calls**: `apps/api/app/billing/stripe_client.py` calls Stripe's REST API directly using `httpx` (already a project dependency) rather than adding the official `stripe` Python SDK. The surface needed — create a Checkout Session, create a Billing Portal session, verify a webhook signature — is small, and this keeps billing consistent with how the rest of the codebase talks to external HTTP APIs (see `packages/ai/translation.py`).
2. **Real webhook signature verification**: `verify_stripe_signature()` implements Stripe's actual documented scheme (`Stripe-Signature: t=<ts>,v1=<sig>`, HMAC-SHA256 over `f"{ts}.{body}"`, with a 300-second replay-tolerance window), not a generic HMAC check against an invented header.
3. **Persisted entitlements, not in-memory**: `CustomerEntitlementModel` and `ProcessedWebhookEventModel` (`packages/database/models.py`) replace the in-memory dicts. Entitlement state is written only by the webhook handler and keyed by email; the API never trusts client-supplied entitlement claims. Kept in a dedicated `BillingRepository` (`packages/database/billing_repository.py`), deliberately separate from `LedgerRepository` — billing is not part of the append-only claim/evidence/resolution domain, and a billing schema change must never be able to touch ledger invariants.
4. **Checkout and self-service cancellation as real endpoints**: `POST /billing/checkout` creates a Stripe Checkout Session (subscription mode, `allow_promotion_codes=true` for the founding-member discount code mechanism from §2.4) and returns its URL for the frontend to redirect to. `POST /billing/portal` creates a Stripe Billing Portal session so a subscriber can change plan or cancel without contacting anyone — this is the "one-click cancellation" requirement, delivered by Stripe's own hosted portal rather than custom-built cancellation UI.
5. **Frontend wired to the real endpoints**: `apps/web/components/pro-cta.tsx` now POSTs to `/billing/checkout` and redirects to the returned URL, with a visible error state instead of the previous "demo build" placeholder. A new `apps/web/components/manage-subscription.tsx` provides the portal entry point. `/pro` shows a post-checkout confirmation or cancellation banner via `?checkout=success|cancelled` query params (Stripe's own redirect mechanism).

## Consequences
- **Positive**: Billing survives a server restart. A webhook replay or redelivery is a safe no-op (idempotency keyed on Stripe's event `id`, persisted, not in-memory). Cancellation is genuinely one-click and self-service, satisfying the "never dark-pattern the cancellation" principle by construction — it is Stripe's own portal, not something this codebase could accidentally make hostile. Verified end-to-end with the API and web servers actually running: `POST /billing/checkout` with no Stripe price configured returns a clean `503` with a specific missing-variable message (not a crash), `POST /billing/portal` for a never-subscribed email returns `404`, and the rendered `/pro` HTML contains the new checkout and portal forms.
- **Negative / follow-ups, stated explicitly rather than silently deferred**:
  - **EU VAT is not handled.** Stripe Tax is not configured. Do not accept real EU consumer subscriptions through this integration until that is resolved or Stripe Tax is enabled.
  - **No accounts system.** Entitlements are keyed by email with no verification that the requester owns that email (anyone can query `/billing/entitlements/{email}` for any address, and anyone who knows a subscriber's email can open their Billing Portal). This is an acceptable minimum for a beta but not for general availability — passwordless magic-link sign-in remains a real, separate piece of future work, not something this ADR claims to have solved.
  - **Dunning** is whatever Stripe's dashboard-configured Smart Retries provide by default; nothing in this codebase configures or overrides it.
  - This integration has been run against Stripe's **test/sandbox mode only** and has not been exercised against a live Stripe account or real card.
