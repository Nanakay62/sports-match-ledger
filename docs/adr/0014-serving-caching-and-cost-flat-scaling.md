# ADR-0014: Serving, Caching and Cost-Flat Scaling

## Status
Accepted

## Context
Handbook §7.1 states the principle plainly: "reader traffic must not touch the expensive parts of the system... achieve this and traffic growth becomes almost free." Auditing the frontend for this ADR found every one of the seven public data-fetching functions in `apps/web/lib/api.ts` (`fetchEvents`, `fetchEventById`, `fetchClaimsByEvent`, `fetchReliabilityScores`, `fetchReliabilityScore`, `fetchClaimsBySource`, `fetchCorrections`) explicitly set `next: { revalidate: 0 }` — zero caching, every single page view re-querying the FastAPI backend and its Postgres database from scratch. This directly contradicts §7.2's precomputation/caching layers and was a real gap, not a documentation-only one, so this ADR both records the decision and fixes it.

## Decision
The seven public fetch functions now use time-based revalidation via Next.js's fetch-level Data Cache (`next: { revalidate: N }`): 60 seconds for high-churn feed/event data (`fetchEvents`, `fetchEventById`, `fetchClaimsByEvent`), 120 seconds for corrections, and 300 seconds for reliability scores and per-subject claim history, which change less often. This is deliberately **not** full-page static generation: every reader page (`/`, `/event/[id]`, `/reliability`, `/reliability/[subject]`, `/topic/[slug]`) reads a `searchParams` prop for language selection, which forces Next.js to render the route dynamically per request regardless of caching — so what's cached is the *data* (the expensive round trip to the API/database), not the HTML response itself. This is a smaller claim than "ISR" in the strict Next.js sense (which caches the rendered page), and this ADR does not overstate it as more than that. All fifteen admin-desk fetch functions (`fetchAdmin*`, same file, after the `ADMIN_API_KEY` boundary) deliberately keep `revalidate: 0` — the editorial review queue and cost dashboard must show live state, not a stale cache, and are explicitly out of scope for this caching layer.

## Consequences
- **Positive**: repeated visits to the same event or reliability page within the revalidation window are now served from Next.js's Data Cache instead of re-hitting Postgres on every request — a direct, verified reduction in backend load for the highest-traffic paths, with the admin desk correctly excluded and still fully live. Confirmed via `npx tsc --noEmit`, lint, and a full production build with no errors after the change.
- **Negative / follow-ups, stated explicitly**: this is fetch-level Data Cache only — no CDN edge layer (Cloudflare, per Handbook §4.5/§7.2's "CDN edge") is configured anywhere in this repository, so cache misses still traverse the full Next.js server render on every uncached request; no purge-on-publish path exists (the handbook's "get the purge-on-publish path right in Phase 9" — §7.2 — is not implemented, so a correction or status change can take up to the revalidation window, not instantly, to appear to a reader who already has a cached view); and no materialised-view/precomputed-page layer exists on the API side (§7.2's "Precomputation" row) — the FastAPI endpoints still compute their responses per call, just less often now. These remain real gaps, not resolved by this ADR, and should be picked up when a traffic-driven scaling trigger (§7.4, `docs/cost-model/infrastructure-tiers.md`) actually calls for them.
